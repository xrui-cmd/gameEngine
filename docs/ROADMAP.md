# 引擎路线图（ROADMAP）

> 本文记录引擎的定位更新与中长期方向：从「轻量 2D 框架」走向「**支持 2D 与 3D 的个人通用引擎**」。
> 维护方式：讨论定案即回填本文；只写方向、红线与驱动项目，**不写具体日期**，进度以实际代码为准。

## 1. 愿景

- **目标**：一个 2D / 3D 通用的个人引擎——现有的 2D 能力继续能用，中期补上 3D 渲染，同一套架构承载后续所有游戏。
- **务实原则**：
  - **游戏 / 示例驱动**：每项通用能力都由真实游戏或示例需求拉动，不为做引擎而做引擎；
  - **小步走**：一次只引入一个新抽象，先在手头游戏里跑通，再谈通用化；
  - **不对标商业引擎**：不追求对齐 Unreal / Unity / Godot 的功能面，只做自己用得到的那部分。

## 2. 现状盘点

引擎仓现有能力（`include/engine/`，均为 2D）：

| 模块 | 职责 |
| --- | --- |
| Entity | 实体基类：位置尺寸 / 帧动画 / 资源三级回退 / 插值快照 |
| Scene / SceneManager | 场景生命周期回调 + 延迟切换 |
| UpdateContext | 固定步长世界上下文（dt / 键盘 / 视口） |
| Config | INI 风格配置解析（容错 + 默认值回退） |
| AudioSystem | SDL3_mixer 音效（RAII + 全链路降级） |
| Font / DebugText | TTF 文本绘制 / 调试文字（DebugText 为 header-only） |
| Rect | AABB 相交判定（header-only） |

缺口（近期路线的靶子）：

- **数学层空白**：没有 Vec / Mat，位置、速度、插值全靠裸 `float`；
- **渲染抽象层空白**：各接口直接暴露 `SDL_Renderer*`，渲染与 SDL 焊死。

## 3. 目标分层

```
┌────────────────────────────────────────────────────┐
│ 游戏框架层：主循环 / 场景组织 / 玩法 —— 宿主已有        │
├────────────────────────────────────────────────────┤
│ 场景与组件层：Scene / Entity / 文本 / 音效 —— 雏形     │
├────────────────────────────────────────────────────┤
│ 渲染抽象层：渲染接口（2D 后端 / GPU 后端）—— 欠缺       │
├────────────────────────────────────────────────────┤
│ 核心层：数学（Vec / Mat）/ 资源管理 —— 数学欠缺         │
├────────────────────────────────────────────────────┤
│ 平台层：窗口 / 事件 / 输入 / GPU 上下文 —— SDL3 托底    │
└────────────────────────────────────────────────────┘
```

- 引擎负责下四层；**游戏框架层永远属于宿主**（主循环与玩法规则不进引擎）。
- 依赖自上而下：上层可替换，下层保持稳定；替换渲染后端不应改动上层。

## 4. 三条架构红线

今后写新代码照此下笔，避免返工。

### 红线一：数学层 header-only、渐进迁移

- 新数学代码一律进 `include/engine/math/`，header-only（无 .cpp、无链接负担）；
- 起步 `Vec2`（算术 / 点积 / 长度 / 归一化）；`Vec3`、`Mat4` 随 3D 需求到来再补，风格保持一致；
- 2D 旧代码**逐处渐进迁移**（插值、碰撞等），不搞一次性重写。

### 红线二：渲染不焊死

- 定义**薄渲染接口**（画纹理 / 画矩形 / 相机变换等），业务代码只依赖接口、不直接摸 `SDL_Renderer*`；
- 2D 后端：`SDL_Renderer`（现有路径收编为该接口的一个实现）；
- 3D 后端：SDL_GPU（一套 API 覆盖 Vulkan / D3D12 / Metal 三后端；配套项目 vendor 内已含 `SDL_gpu.h`）；
- 宁可让接口先带一点 2D 语义，也不提前设计看不懂的 3D 抽象——等第一个 3D 示例再演进。

### 红线三：相机与坐标系语义化

- **Camera 抽象**：2D 相机＝正交投影的特例，3D 相机＝其自然的推广；同一抽象、不同参数；
- **坐标系约定**（写进文档，代码遵循）：
  - 2D：原点在左上、y 轴向下、单位像素（与 SDL 习惯一致）；
  - 3D：右手系、y 轴向上、单位米（进入 3D 时定案并回填本节）；
- 语义定案后，插值 / 裁剪 / 碰撞等坐标相关逻辑一律照此办理，不各写各的。

## 5. 成长路线

### 近期：游戏驱动补通用件（2D 为主）

由下一个游戏的实需拉动，优先级随需求动态排序：

- 输入系统（键鼠抽象）；
- 资源管理（纹理 / 字体统一加载与缓存）；
- 粒子效果（打击感的直接来源）；
- **相机**（跟随 / 平滑 / 边界钳制）——按红线三的姿势写；
- **数学层**（`Vec2` 先行）——按红线一的姿势写。

### 中期：渲染抽象层 + 3D 验证

- 抽出渲染接口，SDL_Renderer 收编为 2D 后端（行为与性能不回退）；
- 增加 SDL_GPU 后端，跑通「**3D 旋转立方体**」示例——证明同一引擎既出 2D 也出 3D 画面；
- 示例收入引擎仓 `examples/`（目录名待定），作为 3D 能力的回归验证。

### 远期：按需推进

- 组件化（向 Entity-Component 方向演进，看游戏复杂度再定）；
- 编辑器、脚本绑定等——有真实需求再开工，不做预先投入。

## 7. 协作与流程

- **双仓舞蹈**（引擎改动进入游戏的固定动作）：

```bash
# ① 引擎仓：完成改动并提交（推送由使用者执行）
git add <本次改动文件>                           # 在引擎仓暂存改动
git commit -m "feat: ..."                       # 在引擎仓提交
# ② 游戏仓：拉取引擎最新提交，更新子模块指针
git submodule update --remote libs/GameEngine   # 子模块路径：libs/GameEngine
git add libs/GameEngine                         # 暂存指针变更
git commit -m "chore: 更新引擎子模块指针"        # 提交新指针，完成联动
```

- **版本标签**：建议自 **v0.2.0** 起给引擎打 tag（此前状态继续以提交哈希钉版本；标签让游戏仓的指针更可读）；
- **单元测试**：暂寄居游戏仓 `tests/`（Rect 碰撞 / Config 解析用例）；待引擎仓具备独立测试工程后迁回。
